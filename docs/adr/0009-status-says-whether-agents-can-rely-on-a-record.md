# Status Says Whether Agents Can Rely on a Record

`status` keeps its one enum. Every value answers whether an agent can rely on the Record: `proposed` means not yet, `accepted` means yes, and `superseded`, `deprecated` and `rejected` mean no longer or never. The life of the thing a Record describes, such as a project that is dormant or finished, goes in a key the Bank declares under `custom_keys`, for example `phase: { type: string, enum: [planned, active, dormant, finished], memory_types: [Context] }`. A dormant project's Record stays `accepted` because the Record is still true. It moves to `deprecated` only when agents should stop using it, and a Record is `proposed` only while it waits for merge review.

A kit-owned lifecycle key was the middle option. It would make `ltm query` decide which values to hide by default, `ltm digest` decide how to group them, and `doctor` decide which checks to skip, and the kit would have to fix one value set for projects, services and experiments, which don't share one. A Bank-declared key leaves those choices with the Bank, and `ltm query phase=active` already filters on it. Splitting `status` into two keys was the expensive option. It needs a new Record schema version and a migration of every Bank. It also means rewriting `ltm accept`, `ltm supersede` and `ltm deprecate`, the `superseded_by` rules in `ltm validate`, `RETIRED_STATUSES` in `ltm query`, the digest's accepted-only filter, and the `status` input of the MCP `query` tool.

Under this convention, `doctor`'s `stale-confirmed` check still flags an accepted Record whose subject is dormant, until someone confirms the Record still holds and sets `last_confirmed`.
